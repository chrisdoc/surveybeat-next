# Spike: Alchemy v2 Effect runtime, TypeScript 7, oxc toolchain (ADR 0008)

Throwaway. Everything lives under `spike/`. Nothing was committed.

**Headline: the code and tooling all work; the cloud deploy (items 7 and 8) is BLOCKED because `~/.alchemy`'s `default` profile has no Cloudflare provider configured.** Items 3 to 6 were therefore proven on Alchemy's local workerd (`alchemy dev`), not on the live `spike29` stage. **No `spike29` stage exists. Nothing was deployed to the account.**

## Versions that actually installed

effect 4.1.2, @effect/sql-sqlite-do 4.1.2, @effect/platform-node 4.1.2 (extra, see below), alchemy 2.0.0-beta.85, @alchemy.run/cloudflare 2.0.0-beta.85 (pulls @alchemy.run/cloudflare-runtime 2.0.0-beta.85, @distilled.cloud/cloudflare 1.0.0-rc.18, rolldown 1.2.13), typescript 7.0.2, @effect/tsgo 0.67.4 (npm `latest`), oxlint 1.92.0, oxlint-tsgolint 7.0.2006, oxfmt 0.77.0, @types/node 26.6.6 (extra). Node v26.13.0, pnpm 12.18.0, linux arm64. Every pin installed as requested. `@effect/vitest` is in the catalog but unused.

Setup facts:

- `pnpm install` fails with `ERR_PNPM_IGNORED_BUILDS` until `workerd` is allowed (`allowBuilds: { workerd: true }` in `pnpm-workspace.yaml`, written by `pnpm approve-builds --all`).
- `alchemy` needs the peer `@effect/platform-node` and will not run without it ("could not load the required peer dependency"). It is not installed automatically. Pin it with the other `@effect/*` at 4.1.2.
- `pnpm peers check` warns that `capnp-es` (inside alchemy) wants typescript `^5.7.3 || ^6.0.0`. Harmless so far.
- @effect/tsgo 0.67.4 lists oxlint `1.88.0` to `1.91.0` as supported. We pin 1.92.0. We did not use `effect-tsgo oxlint`/`patch`, so no impact seen.

## Verdict on ADR 0008

- **TypeScript 7.0.2 with `tsc -b`: stands.** Project references, the strict option set and `types: []` for `domain` all work. One gotcha for the ADR: the Effect plugin entry is `@effect/language-service` and it only loads through `effect-tsgo tsc` or `effect-tsgo diagnostics`, not plain `tsc`. Turn off `unstableApiUsage` or every Effect HTTP and SQL call fails the build.
- **oxlint (jsPlugins, type-aware) and oxfmt: stand.** The custom boundary rule works in the plain ESLint rule API, and tsgolint 7.0.2006 runs against TS 7.0.2 projects. Watch the `require-yield` hit on `Effect.gen` bodies with no yield.
- **Alchemy v2 Effect runtime kept in the adapters: stands on local evidence, not yet confirmed on Cloudflare.** `Cloudflare.DurableObject` with `@effect/sql-sqlite-do` (transactions, both migrators, WITHOUT ROWID, alarms), the HttpApi Worker, Queue + DLQ consumers and the Submission Worker props all worked in `alchemy dev` with the exact pins. Costs found: the `@effect/platform-node` peer must be pinned too; the docs' `HttpPlatform` stub is stale; the Submission Worker's logging defaults are ON unless set explicitly. The remaining risk the ADR named (deployed behaviour, deployed cold start, Observability API check of the Submission Worker) is untested until someone logs the default profile into Cloudflare. Items 7 and 8 should be rerun before ADR 0008 is called verified.
