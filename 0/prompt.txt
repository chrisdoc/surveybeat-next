<result>The failing privacy property test now passes. The failure was a real gap in `enforceEffectiveNOnResult`: it could show a Dimension's Typical change where a fresh computation at N gives none.

## Cause
`calculateRoundResult` now hides an earlier Dimension's score unless every Question it averaged still meets the raised N (`pastDimMeetsN`). My masking in `enforceEffectiveNOnResult` only checked the Dimension's own contributor count. Its Typical change also stayed visible when an earlier Question score, used in the Dimension's per-Question changes, was newly hidden.

The generator does build Dimension and Question history independently, but this is possible in real data too. A Dimension can have at least N distinct contributors while every one of its Questions has fewer. That happens when the stored N was lower and each Submission answered a different Question. So the fix is not just working around an impossible fixture.

## Change
Only `packages/domain/src/rounds/Results.ts` changed, inside the Dimension masking in `enforceEffectiveNOnResult`.
- **Earlier Dimension trend points:** a score is kept only if the Questions that averaged into it (from the Questions' own trends) match its `usableQuestionCount` and all meet the effective N. This mirrors `pastDimMeetsN`.
- **Stale values:** the Dimension's `change` and `typicalChange` are now nulled when an earlier Question score in that Dimension was newly hidden, not only when the Dimension's own point was.

## Decision
When `enforceEffectiveNOnResult` hides a Typical change, it sets it to null instead of recomputing it. Recomputing would need each earlier Round's raw Question scores and contributor counts, and a stored Result only keeps the 12-Round trend. A fresh computation can therefore show a Typical change where the enforced one shows none. That is over-masking, not a leak, and the test only forbids showing something the fresh result doesn't. I did not edit the test.
