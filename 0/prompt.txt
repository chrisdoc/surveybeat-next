**Things you asked about that hold up**

- **No send bypasses the wrapped store.** Every send path in the DO (`Organization.ts` 402, 538, 588, 681, 1132, 1424, `SqlDirectory` `EmailRequested`, and `requeue` in `EmailVisibility`) goes through the wrapped `sends`. The only `INSERT INTO email_send` is in `SqlSendRepository`, behind the wrapped store.
- **Rolled-back transactions.** The outbox row is inserted inside the same `sql.withTransaction` as the send, so it rolls back with it. A rollback can leave `setAlarm(now)` behind, which is harmless: the alarm fires, finds nothing to do, and `repairAlarm` resets it.
- **Rows inserted during the `sendBatch` await.** `DELETE ... WHERE id &lt;= last.id` removes only the rows that were sent. Rows added while the await was open stay. The create path then calls `repairAlarm`, which sets an alarm, and the final `repairAlarm` in the handler re-arms it.
- **Crash between `sendBatch` and `DELETE`.** This produces duplicate queue messages. The consumer acks on every non-retry path, and `claim` makes each send run once.
- **No loop or starvation in `repairAlarm`.** With rows waiting it targets `min(now, nextJob)`. After a drain the handler's final call sets the next job time or deletes the alarm. A permanently failing `dispatch` throws, and the platform's alarm retry is bounded.
- **Re-created sends.** `create` on an existing send returns the stored state, so a repeat of a Pending send adds a harmless extra outbox row.
- **`id != ''` for `except = null`.** This is correct. Round ids are never empty, so every Round of the Pulse is returned. The `UNION` also deduplicates dates.
- **`nextRoundSlot` semantics.** It keeps the old behaviour: the team-local date, the `openInstant &lt;= now` rule, and `+7` days per unavailable date, which preserves the weekday. Including every Round status matches `UNIQUE(pulse_id, planned_open_date)`. When the next Round is scheduled right after one opens, that Round's date is always at or before today, so it cannot collide.
- **`SqlRounds.updateScheduledRound` now writes `planned_open_date`.** This fixes the stale date that `executeOpenJob` used to schedule Invitations.
- **Privacy.** `email_outbox` stores only `send_id`. It holds no Person, submission or time data that SPEC §7 or ADR 0005 protect.

**Findings**

- **MINOR — `packages/cloudflare/src/Organization.ts:1044-1050`, alarm handler.** Platform alarm retries are bounded. If the Email queue is unavailable for longer than that, the alarm handler gives up and `email_outbox` rows sit there with no alarm. The next send creation, job run or `repairAlarm` call recovers them, and `runDueJobs` already had this weakness. Invitations would be late, not lost. A cheap hardening is to call `repairAlarm` once during DO activation, after `migrations.apply`, so a restarted DO re-arms itself. This is optional and does not block the merge.
- **MINOR — `packages/cloudflare/src/organization/EmailOutbox.ts` `dispatchBatch`.** A row that can never be encoded would block the whole outbox. Examples are a `send_id` that fails decoding or a missing `organization` row. `Effect.die` makes every alarm run fail until the retries stop. It is unlikely, because `send_id` is only written from a typed `SendId` and the organization row exists before any send. If you want to be defensive, delete or skip undecodable rows rather than dying.

The follow-up of removing the Worker-side queuing should get a ticket, so the double enqueue does not become permanent.
