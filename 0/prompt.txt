## Decision, write it as docs/adr/0028-offboarding-returns-no-results.md

Article 28(3)(g) return of data does not give an Organization admin every Team's Results. ADR 0003 stands: the admin role grants no access to Results, comments, or Actions without a Membership. ADR 0014 is unchanged. The offboarding export contains only records an Organization admin can already administer:
- Organization id, name, minimum group size, AI processing flag, default locale
- Teams: id, name, time zone
- People: id, email, organizationAdmin, locale, time zone, removedAt, erasedAt. An erased Person already has the tombstone email. Do not recover an original address.
- Memberships, including ended ones: id, team id, person id, role, startedAt, endedAt
- Pulses and their Questions (wording and settings), because team.viewPulses and team.editPulse already include admin

The export contains no Result, comment, theme, Action, Note, Submission, Answer, participation, Invitation token, token hash, Edit key, email body, auth user id, or session. Anonymous aggregates are destroyed with the tenant, not handed to an admin who has no Membership. A Lead downloads nothing new here; they use the product before offboarding.

Deletion is irreversible and is allowed when the caller is the sole Organization admin. It is not LastAdmin and not LastLead. Cloudflare PITR copies are not deleted by the app. The confirmation UI says they expire after Policy.backupRetentionDays (30). Say that in the ADR.

## Crash order

D1 migration packages/cloudflare/d1-migrations/0012_organization_offboarding.sql. New file. Add its SHA-256 to d1-migrations.lock.json. MigrationHistory.test.ts prints the lock line if the hash is wrong.

CREATE TABLE organization_offboarding (

  actor_user_id TEXT NOT NULL,
  confirmed_at INTEGER NOT NULL

Handler order:
1. Resolve the session and the Organization the way currentMember does.
2. If the Durable Object still has this Person and they are an Organization admin, require the typed name, then insert organization_offboarding for that auth user id. If the row exists, it must be the same auth user id.
3. If the Durable Object no longer has the Person, continue only when organization_offboarding.actor_user_id is the session user. Do not ask for the name again.
4. Anyone else is Forbidden. A wrong name does not write the row and does not delete anything.
5. Delete this Organization's D1 invitation_index, test_invitation_index, test_submission_index, submission_index, and auth_session_organization. Tokens and Edit keys then fail closed in PageRoutes and SubmissionRoutes.
6. Call the Durable Object wipe.
7. Read person_index.auth_user_id for this Organization before deleting those rows. Delete captured_email where message_id is in this Organization's email_message rows, then delete those email_message rows. Never delete captured_email by recipient. Then delete person_index, organization_claim, organization_offboarding, and organization_index for this Organization.
8. For each collected auth user id, call the existing eraseAccount path. It already keeps the account when any person_index row remains, including removed_at set. Do not copy that SQL.

Do not delete auth_organization, auth_member, or auth_invitation. Those are unused Better Auth plugin tables (ADR 0022), not SurveyBeat Organizations.

A crash after the wipe and before the D1 person_index delete must be finishable by the same admin, because the offboarding row remains and the Durable Object wipe is idempotent. A crash before the offboarding row writes nothing. Another Organization's rows and the other Organization's Durable Object stay. Person erasure behavior stays as ADR 0027.

1. `packages/cloudflare/src/auth/D1OrganizationOffboarding.ts` (`removeIndex`) can leak an auth account on retry. `person_index` is deleted before `organization_offboarding` and `organization_index`, and the statements are not batched.
