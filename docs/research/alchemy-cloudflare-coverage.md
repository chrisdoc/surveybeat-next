# Alchemy: Cloudflare resource coverage, per-PR stages, state, local dev and tests

Research for issue #8 (map #1). Checked 2026-11-07.

## Version researched

- **`alchemy@2.0.0-beta.85`** (npm `latest` tag, released 2026-11-02) together with **`@alchemy.run/cloudflare@2.0.0-beta.85`**. Source checked at `alchemy-run/alchemy@d096cad` (2026-11-06).
  - npm: https://www.npmjs.com/package/alchemy
  - Release: https://github.com/alchemy-run/alchemy/releases/tag/v2.0.0-beta.85
- **Read this first.** Alchemy now has two lines. Most older blog posts and examples describe v1.
  - **v2 ("Infrastructure as Effects")** lives at https://github.com/alchemy-run/alchemy, with docs at https://alchemy.run. The stack is an `Alchemy.Stack(...)` built from `Effect.gen` programs, and each cloud is its own package (`@alchemy.run/cloudflare`, `@alchemy.run/github`, ...). It requires **Effect 4** (`effect ^4.1.0`, see `pnpm-workspace.yaml` catalog). v2 is still in **beta**, but npm `latest` points at it.
  - **v1 (async/await)** has moved to https://github.com/alchemy-run/alchemy-async. `github.com/sam-goodwin/alchemy` now redirects there. Its last release is `v0.94.0` (2026-08-01), with docs at https://v1.alchemy.run. Migration guide: https://alchemy.run/migrating-from-v1
- SPEC §6 picks Effect for all logic, so v2 fits well. Resources, bindings and runtime clients share one Effect program, and the bindings are typed Effect services. **Recommendation: build on v2, pin an exact beta version, and expect breaking changes between betas.**

Below, "src:" links point to `https://github.com/alchemy-run/alchemy/blob/d096cad7e5506a57aa829dad97079eb94ff4af08/packages/cloudflare/src/...` (written as `cf/...`).

## 2. Stages and per-PR previews

**Stage model.** A stage is an isolated instance of a Stack, with its own state and its own physical names, for example `myapp-pr_147-photos-9b2c`. If you pass no stage, `alchemy deploy` defaults to `live_$USER`, `alchemy dev` to `dev_$USER`, and tests to `test_$USER`. Names must match `[a-z0-9][-_a-z0-9]*`. The stage is resolved from `--stage`, then `$ALCHEMY_STAGE`, then the default. Code can branch on it with `yield* Stack` → `stack.stage`, for example `RemovalPolicy.retain(stack.stage === "prod")` or `protect`. Sources: https://alchemy.run/environments/stages, src: `packages/alchemy/src/RemovalPolicy.ts`.

A PR stage gets its own Workers, D1 databases, DO namespaces (because the Worker is separate), queues, buckets and so on. This matches SPEC §6.4 directly.

**GitHub Actions (official pattern).** https://alchemy.run/environments/ci

- Trigger on `push: [main]` and `pull_request: [opened, reopened, synchronize, closed]`. Use `concurrency: deploy-${{ github.ref }}` and `cancel-in-progress: false`.
- `STAGE: ${{ github.event_name == 'pull_request' && format('pr-{0}', github.event.number) || (github.ref == 'refs/heads/main' && 'prod' || github.ref_name) }}`
- The `deploy` job runs `alchemy deploy --stage $STAGE` when the action is not `closed`. The `cleanup` job runs on `closed` and does `alchemy destroy --stage $STAGE`. It includes a safety check that refuses `prod`.
- A `GitHub.Comment` resource with a stable logical ID posts the preview URL and updates it on each push. It uses `GitHub.GitHubEnv` and `GITHUB_TOKEN` with `pull-requests: write`.
- "Credentials as code": a separate `stacks/github.ts` is deployed once with an `admin` profile. It mints a scoped `Cloudflare.ApiToken.AccountApiToken` and writes it to the repo with `GitHub.Secret` / `GitHub.Variable`. Run `alchemy provider check-env` as the first CI step to fail fast.
- **Composite action:** the repo root has an `action.yml` (`uses: alchemy-run/alchemy@main`, mentioned in the beta-62 blog post). It decides deploy, destroy or skip by itself. Note that it names PR stages **`staging-<n>`**, not `pr-<n>` as the docs do. Pin a SHA if you use it, or just copy the workflow above. Source: https://github.com/alchemy-run/alchemy/blob/d096cad7e5506a57aa829dad97079eb94ff4af08/action.yml

**Worker Previews (`preview.of`) are a different thing.** They are Cloudflare's per-branch copy of one Worker, with its own URL and its own DO state. However, "Service bindings from a Preview resolve to production; **crons, queue consumers, and production routes stay on production**. For an end-to-end multi-Worker PR, deploy a full stage instead." Because SurveyBeat depends on Workflows, Queues and Cron, **use full stages per PR, not `preview.of`.** Source: https://alchemy.run/cloudflare/compute/previews

**Teardown gotchas for PR stages:**
- R2 buckets need `forceDestroy: true`, or a destroy with objects present fails.
- Secrets Store secrets need stage-specific names (see §1). The store itself is never deleted.
- Zones are `retain` by default. Keep the zone in a shared stack and give PRs subdomains, or just use `workers.dev`.
- Turnstile widget domains must cover PR hostnames.
- Open issue #2921 asks for "destroy several stages in one process". Today there is no built-in sweeper for orphaned `pr-*` stages, for example when a cleanup job failed. Workaround: a scheduled job that runs `alchemy state list` and destroys stages whose PRs are closed. CLI reference: https://alchemy.run/cli/state

## 3. State in CI

- **Default:** local files in `.alchemy/state/<stack>/<stage>/*.json`. Gitignore them. This is fine for solo work but useless on ephemeral CI runners.
- **`Cloudflare.state()` (recommended):** an `alchemy-state-store` Worker in your account, backed by a **Durable Object with embedded SQLite**. State is encrypted at rest with a key, and the bearer token is kept in your **Secrets Store**. The first local run bootstraps it. **In CI (`CI=true`) a missing store fails the run on purpose**, so provision it once with `alchemy state bootstrap --profile <ci-profile>`. In CI, credentials are resolved from the Secrets Store on each run through a short-lived edge-preview Worker, so nothing is persisted. `Cloudflare.state({ workerName })` gives you a separate store. Source: https://alchemy.run/state-store
  - The test-harness page calls `Cloudflare.state()` "R2-backed". That is outdated. The source (`cf/StateStore/Store.ts`) is a Durable Object.
  - Open issue #2805: `Cloudflare.state()` cannot use a different account than the Cloudflare providers.
- Alternatives: `AWS.state()` (DynamoDB), `GCP.state()` (GCS), or a custom store (https://alchemy.run/state-store/custom-state-store).

## 4. Local dev mode

- `alchemy dev` (default stage `dev_$USER`) runs Workers in **workerd directly**, with Alchemy's own simulators in `@alchemy.run/cloudflare-runtime`. **It is not Miniflare.** Miniflare appears only in Alchemy's private test tools. SPEC §6.3's "Miniflare, through Alchemy's dev mode" is slightly off: the emulation is workerd-based, but it is not Miniflare. v1 did use Miniflare (`alchemy-async/alchemy/src/cloudflare/miniflare/`). Source: https://alchemy.run/cloudflare/local-development, src: `packages/cloudflare-runtime/package.json` (depends on `workerd`, not `miniflare`).
- **Emulated locally:** Workers (with hot reload), Durable Objects including SQLite, KV, R2 (plus an S3 endpoint), D1 (migrations applied on every reconcile), Queues + consumers (batching, retry, **dead-letter semantics**), Workflows ("real step semantics"), Secrets Store (seeded with real values), and Vite and other framework dev servers with HMR. Crons fire on schedule, and `/cdn-cgi/handler/scheduled` triggers them manually. Email `send_email` writes `.eml` files, and `POST /cdn-cgi/handler/email` drives inbound mail.
- **Not emulated:** Workers AI is a remote binding (real calls, billed). Analytics Engine is a no-op stub. Turnstile has no simulator. DNS and Vectorize deploy to the cloud in your personal stage.
- `Alchemy.remote()` opts a single resource out of emulation, for example a real queue or real email. Moving a resource between local and live plans a **replacement**.
- Open issues: #2810 (mixing local and remote is hard to get right), #2884 (local R2 S3 credentials are rejected by S3 clients), #2879 (binding clients fail when the env name differs from the logical ID).

## 5. Vitest integration

- `@alchemy.run/test` provides `Test.make({ providers, state, stage, dev })` with adapters for `alchemy-test`, `bun test` and **Vitest** (`@alchemy.run/test/Vitest` + `@effect/vitest`, where each test is an `it.live`). `deploy(Stack)` / `destroy(Stack)` run the real stack. **`dev: true` runs it against the local workerd simulators instead of the cloud.** The test stage defaults to `test_$USER`, or set `ALCHEMY_TEST_STAGE=ci-pr-42`. Sources: https://alchemy.run/testing/test-harness, https://alchemy.run/testing/testing-a-stack, https://alchemy.run/cloudflare/tutorial/part-4
- **Gap:** tests run in Node (or Bun) and drive the stack over HTTP or RPC. This is integration-style testing. Alchemy has **no integration with `@cloudflare/vitest-pool-workers`**: no grep hits in the repo, and no wrangler-config generator in v2 (v1 had `WranglerJson`). To unit-test DO or adapter code inside the isolate (calling `runInDurableObject` or reading storage directly), you would need a separate test-only wrangler config for vitest-pool-workers, which works against SPEC's "no hand-edited wrangler config". **Workaround (recommended):** keep domain logic in plain Node tests, as SPEC already requires. Test the adapters through `Test.make({ dev: true })` against small test-only RPC methods or HTTP routes in the stack. Run a smaller `Test.make()` cloud smoke test on the PR stage.

## 6. Gaps and workarounds (summary)

1. **v2 is beta.** Pin an exact version and budget time for API churn. v1 is in maintenance in a separate repo.
2. **Secrets Store names are not stage-scoped.** Set `name` per stage, or use Worker `secret_text` through `Config.Redacted`.
3. **R2 PR teardown fails if a bucket is not empty.** Set `forceDestroy` for non-prod stages.
4. **The DLQ needs its own consumer.** Cloudflare does not alert on dead-lettered messages.
5. **Worker Previews do not carry crons or queue consumers.** Use full `pr-<n>` stages.
6. **No stage sweeper.** Add a scheduled cleanup for orphaned PR stages (#2921).
7. **Dropped Worker secrets linger** (#2800). Rotate or delete them by hand when you remove one.
8. **Local dev:** Workers AI is remote (billed), Analytics Engine is a stub, and Turnstile has no simulator. Mock `LanguageModel` and use Cloudflare's Turnstile test keys.
9. **No vitest-pool-workers integration.** Alchemy's Vitest adapter tests deployed or local stacks from Node.
10. **Analytics Engine queries** are not wrapped by Alchemy. Call Cloudflare's SQL API yourself.
11. **Email:** Alchemy has the resources, but whether Cloudflare Email Sending can reach arbitrary recipients and how good deliverability is are Cloudflare questions for the email ticket.
12. Docs disagree with each other in places: the `action.yml` stage name is `staging-<n>` versus `pr-<n>` in the docs, and the test-harness page says the state store is "R2-backed". Trust the source code.
